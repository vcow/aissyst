# Контекст проекта aissyst

Обновлено: 29 октября 2026 года. LLM-запросы переведены на последовательный обмен без stream_id; добавлены IsBusy и экстренная отмена CancelAsync. Минимальный реальный inference без stream_id успешен; полный сценарий приложения ещё требует проверки.

## Назначение и платформы

- Приложение помогает вести диалог: захватывает аудио, транскрибирует локально через Whisper и по запросу пользователя обращается к LLM за переводом, подсказкой или ответом.
- Два собеседника однозначно определяются источниками: микрофон — пользователь/экзаменуемый (`interviewee`), приложение — собеседник/экзаменатор (`interviewer`). Определение нескольких говорящих внутри источника сейчас не требуется.
- Текущая платформа — macOS; Windows предусмотрена архитектурой, её аудиозахват ещё не реализован. iOS в проекте нет.
- .NET 10, Generic Host, DI. Кроссплатформенная координация находится в `aissyst.core`, консольный интерфейс — в `aissyst.console`.

## Аудио и транскрибация

- Источники непрерывно прослушиваются во время сессии. Начало аудиофрагмента определяется входным сигналом; тишина сама по себе запись не начинает.
- Завершение фрагмента: тишина, хоткей или достижение `MaxRecordingDuration`. Прослушивание после этого продолжается.
- Лимит считается по PCM-сэмплам с учётом частоты и числа каналов. Большой входной буфер делится с сохранением остатка для следующих фрагментов.
- В `ApplicationSettings` лимит по умолчанию 30 секунд; в текущем `Program.cs` явно установлено 15 секунд. Таймаут тишины — 1 секунда.
- `WhisperTranscriber` использует английскую `small.en-q5_1`; модель загружается при отсутствии в локальном кеше, проверяется SHA-256 и не хранится в Git.
- В `Program.cs` оба лимита обработки установлены в 1. Параллельную работу одного экземпляра Whisper не включать без отдельной проверки.
- Переполнение очередей удаляет самые старые ожидающие элементы с сообщением в журнале. Очистка очередей не отменяет уже выполняющуюся обработку.
- По решению пользователя совпадения временных меток транскрипций считаются допустимым редким риском для текущего сценария. При отказе SortedSet добавить сообщение с уже имеющейся меткой контроллер пишет Warning с временем и источником, без текста транскрипции. Поведение очереди и DTO не менять ради этого случая; вопрос закрыт этим предупреждением.
- `ICaptureSession` публикует аудиозаписи через события `MicrophoneRecordingCompleted` и `ApplicationRecordingCompleted` с `IReadOnlyList<AudioFrame>`; контроллер передаёт их в транскрибатор и текстовый процессор. При завершении контроллер явно отписывается от событий, ожидает задачи и освобождает семафоры/источник отмены. `ConsoleCaptureSession.Dispose` очищает обработчики. Пакет R3 и его типы удалены из исходников.
- `CaptureSession` создаётся в дочернем DI scope; уничтожение scope останавливает захват. После остановки перед сохранением текста ожидается завершение обработки оставшихся аудиофрагментов.

## Текстовый процессор и вывод

- Вместо текстовых кортежей используется immutable record `DialogMessage(Timestamp, Source, Text)`.
- `ITextProcessor.Process(DialogMessage)` сохранён как синхронный совместимый метод. Контроллер использует `ProcessAsync(message, cancellationToken)` и ожидает сохранение в БД. Возвращается законченная реплика или `null`.
- Исходные фрагменты всегда добавляются в буфер несохранённых записей и историю памяти без обрезки пробелов/переносов и без объединения (включая пустые). Каждая новая запись запускает попытку сохранить весь буфер одной транзакцией; только успех очищает буфер. Ошибка БД логируется и не мешает фиксации фрагмента в памяти. В памяти также хранятся исходные тексты; представление реплик нормализуется при обработке и чтении. Метки времени согласованы с SQLite как UTC.
- Фрагменты одного источника объединяются. Реплика считается законченной при поступлении непустого сообщения другого источника; пустой текст её не завершает.
- Незавершённая реплика доступна в истории, но не выводится как завершённая до смены источника.
- `GetDialog(fromTime)` возвращает снимок сообщений с `Timestamp > fromTime`, сортирует их по времени и объединяет соседние сообщения одного источника. Метка объединённой реплики соответствует последнему включённому фрагменту.
- `TextProcessor` восстанавливает историю выбранной сессии через `IDatabase.GetSessionAsync`. Роли `interviewer`/`interviewee` преобразуются в источники приложения/микрофона; прочие роли — в `None`.
- Восстановленные записи не выдаются повторно как новые законченные реплики. Контроллер очищает отображение и пакетно выводит полную историю при запуске и реконнекте, включая незавершённую реплику.
- `IOutput` отвечает за пользовательский вывод (`Clear`, `PrintMultipleDialogMessages`, `PrintDialogMessage`, `PrintLLMAnswer`); `ConsoleOutput` зарегистрирован в DI. Логгеры используются для служебных сообщений и ошибок.
- Дополнительный `SessionFileTextProcessor` находится в `aissyst.console`, не в core. Он сохраняет отдельные `microphone.txt` и `application.txt` в уникальной папке `transcripts/session-…` при завершении сессии. В файлах только текст одной строкой.
- `ISessionTextProcessor` удалён. Дополнительные методы файлового процессора вызываются напрямую из `MainThreadWorker` после приведения типа; контроллер предоставляет общее `WaitForIdleAsync`.
- Сейчас в DI выбран обычный `TextProcessor`, файловый процессор остаётся альтернативной реализацией.

## Сессия и LLM

- `ISessionSelector.InitializeAsync` выбирает сессию один раз. Затем модель и процессор синхронно получают её ID через `GetSelectedSessionId()`.
- Контроллер инициализирует селектор до модели/процессора. При подключённой модели она инициализирует процессор; отдельная перегрузка `InitializeAsync(sessionId, …)` удалена.
- `SessionModel` загружает вводную и тематический контекст из БД, получает восстановленный диалог из процессора и формирует `Session` для LLM.
- DTO описаны в `aissyst.core/LLMConnector/DTO`. `DTO-fields.txt` удалён пользователем в текущих изменениях; не восстанавливать автоматически. Пример начальных инструкций и протокола находится в `contexts/template/agent_initial_instructions.txt`.
- Пользователь унифицировал идентификатор: `Session`, `DialogRequest` и `DialogResponse` имеют поле `request_id` / свойство `RequestId`. Прежнее поле запроса `id` больше не актуально. `DialogRequest` также содержит `summary`, `raw_records` и тип запроса; ответ — `error`, `summary`, опциональный `summary_ts`, `message`.
- Саммари обновляется при каждом успешном ответе. В него входит состоявшийся диалог, но не сгенерированная подсказка, которую пользователь мог не произнести.
- `summary_ts` задаёт последнюю включённую в саммари реплику. Следующий запрос включает только сообщения с более поздней меткой. При пустом `raw_records` метка отсутствует; прежняя подтверждённая граница сохраняется.
- Для `summary_ts` добавлен nullable DateTime JSON-конвертер: отсутствие, JSON null и пустая/пробельная строка дают null; некорректная дата вызывает ошибку. При сериализации null поле опускается.
- Ответ проверяется относительно отправленного снимка. Не допускается смещение границы на ещё не отправленные сообщения или стирание существующего саммари пустым ответом.
- Актуальность ответов определяется `request_id`, а не только временем: разные запросы могут охватывать одинаковый диалог. Устаревшие и повторные ответы не применяются.
- Отправленный снимок не должен изменяться при продолжении той же реплики. Строгое чередование источников в списке не является обязательным условием.
- `md_format` разрешает Markdown только внутри ответного поля `message`, для удобства чтения пользователем. Входной контекст и `summary` не требуют Markdown.

## Хоткеи

Настраиваются в `ConsoleHotkeySettings`; при запуске выводится подсказка.

- Enter — начать прослушивание.
- Space — завершить текущие аудиофрагменты и продолжить прослушивание.
- S — остановить прослушивание.
- C — очистить ожидающие аудиозаписи и транскрипции с выводом количества удалённых элементов.
- Q / Ctrl+C — завершить приложение.
- 1 — перевод последней реплики собеседника на русский.
- 2 — подсказка для ответа на английском.
- 3 — полноценный ответ на английском.
- 4 — перевод и подсказка.
- 5 — перевод и полноценный ответ.

Запросы помощи доступны во время прослушивания и между сессиями записи. В режиме перенаправленного ввода после команды нужен Enter.

`ApplicationController.SendRequestAsync` выполняет запрос без блокирования чтения клавиатуры, обновляет модель и выводит ответ через `IOutput`. Новый запрос при занятом коннекторе отклоняется с InvalidOperationException. Одновременно выполняется один LLM-запрос, без очереди. Принимается корректный успешный ответ с request_id выше последнего принятого; ошибочный ответ границу не меняет, устаревшие ID игнорируются. Ошибки журналируются. Запросы LLM отслеживаются отдельно от обработки аудио: `WaitForIdleAsync` не ждёт их, а завершение контроллера отменяет и ожидает их.

`HostOptions.ShutdownTimeout` установлен пользователем в 3 секунды.

## Подключение ChatGPT: что реально готово

- Реализован вход Sign in with ChatGPT через системный браузер, loopback callback, PKCE и проверку ID-токена.
- Реальный вход в аккаунт успешно проверен; разрешение на использование плана получено. Повторный запуск использует сохранённую сессию без браузера.
- Секреты сохраняются вне репозитория; не читать и не выводить содержимое файлов учётных данных без необходимости. Токены и URL с ID token hint не журналировать.
- Первый реальный запуск дошёл до WebSocket, но сервер отклонил warmup с HTTP 400; точная причина в прежнем логе была потеряна. `ResponsesApiException` теперь сохраняет status/code/type/message/param/request_id, включая ошибки без code и с detail. Транспорт журналирует их вместе с моделью, типом события и response ID; response.failed и response.incomplete сохраняют серверную причину. Полные исходящие запросы и заголовки авторизации не выводятся. Повторный лог выявил Unsupported parameter: stream_id. Два разрешённых пользователем минимальных реальных запроса к gpt-6.1-sol подтвердили: с stream_id — HTTP 400, без него — response.completed и OK (14 токенов). Проверка выполнена отдельным скриптом в /private/tmp/aissyst-ws-probe, без персонального контекста. Поддержка warmup, продолжения и полной JSON-схемы в реальном приложении ещё не подтверждена.
- `ChatGPTConnector.InitializeSession` и `SendRequest` реализованы через Responses API WebSocket; подробности и границы проверки ниже.
- Хоткеи, применение ответа, отмена и вывод проверены с тестовым коннектором, а не реальным inference-запросом.
- Пользователь подтвердил план: **Responses API через WebSocket с авторизацией Sign in with ChatGPT**. Под это обсуждались начальная отправка контекста и последующие запросы. HTTP со streaming был приведён ассистентом из документации, но не принят как изменение архитектуры. Не представлять выбор транспорта как открытый вопрос без новых оснований.
- WebSocket-транспорт реализован по текущей официальной документации и ограничениям SiWC. Авторизация не обеспечивает постоянное хранение контекста; восстановление использует локальную историю.

### WebSocket-коннектор: текущая реализация

- Документ `contexts/codex_websocket_implementation.md` пользователь считает рекомендацией, а не обязательным ТЗ. Приоритет у текущих DTO и решений в диалоге. Не менять `SummaryTimestamp` на string; отдельный revision не нужен. Keychain не добавлять.
- Добавлены `IModelSelector`, `LLMModel` в core и `ConsoleModelSelector` в console, зарегистрированы в DI. Коннектор после OAuth получает аккаунтный `GET /v1/models`, отбирает `visibility=list`, показывает display_name, использует выбранный slug. Жёстко заданной модели нет.
- Выбор reasoning effort обсуждён и отложен пользователем до исправления подключения; пока параметр reasoning не передаётся. CancelAsync добавлен в интерфейс коннектора; отдельный консольный хоткей экстренной отмены пока не назначен.
- `ILLMSessionLifecycle` удалён вместе с callbacks ConfigureSession/acceptResponse/acceptRecovery и ConfigureDialogRestoration. `ILLMConnector` имеет IsBusy, InitializeAsync, ReconnectAsync, CancelAsync, InitializeSession(instructions, Session), SendRequest(DialogRequest, continuation) и обычное событие ConnectionLost. Коннектор не вызывает модель и не принимает решений о подтверждении ответа.
- Ответ коннектора — LLMResponse(Payload: DialogResponse, Continuation: ILLMContinuation). Продолжение непрозрачно для core, содержит ConnectionId, IsValid, Retain/Dispose. В провайдере это независимые Retain/Dispose-указатели на серверный response.id и socket. Именованных потоков и закрепления серверного кеша больше нет; при previous_response_not_found выполняется восстановление. DTO Session/Request/Response не менялись.
- `SessionModel.SendRequestAsync` формирует снимок и сохраняет локальные параметры запроса в async-операции, удерживает копию continuation, ждёт сеть вне блокировки, сам проверяет request_id/error/summary/summary_ts. При успехе под Lock заменяет один immutable ConfirmedState (ID, summary, граница, continuation); ошибка оставляет прежнее состояние, устаревший ответ возвращает null. Отдельные публичные GetRequest/Reset/IsCurrentResponse/CompleteRequest удалены. GetSession оставлен для снимка полной Session.
- Контроллер вызывает только model.SendRequestAsync и выводит ненулевой ответ. `_lastPrintedAnswerId` — только защита порядка отображения уже принятых ответов при переупорядочении task continuations; бизнес-решение принимает только модель.
- `DialogCoordinator` — общий DI singleton для модели и контроллера, оборачивает ITextProcessor и синхронизирует ProcessAsync/ReloadAsync вместе с уведомлениями MessageCompleted/HistoryReplaced. Контроллер подписывается для одиночного вывода либо Clear + пакетного вывода; модель и процессор не обращаются к IOutput. Callback восстановления в контроллер удалён.
- `ResponsesSocket` — ClientWebSocket, Authorization Bearer, TLS, keepalive и сборка фрагментированных текстовых сообщений. `ResponsesConnection` — один reader и последовательные операции; `ResponsesProtocol` — создание событий и проверка ответов.
- На новом соединении warmup (`developer`, `generate=false`), затем JSON Session (`user`), затем JSON DialogRequest. `store=false`, без stream_id, JSON Schema при генерации. Успех требует response.completed/status=completed; частичные deltas не применяются. Refusal, ошибки API, неверный JSON/структура/request_id/summary_ts не коммитят состояние.
- Серверный ID previous_response_id скрыт в continuation. Коннектор не хранит отдельный confirmedResponseId: подтверждённый указатель принадлежит SessionModel рядом с саммари. Транспорт проверяет структуру JSON, модель — смысл и актуальность ответа.
- По последнему решению пользователя параллелизм LLM удалён: один активный запрос, без очереди и без stream_id. Транспорт хранит один Pending и сопоставляет события по response.id; пулы потоков, слоты, fork и drain удалены. IsBusy выставляется атомарно до начала операции и сбрасывается в finally; попытка нового SendRequest/InitializeSession при занятости вызывает InvalidOperationException. SessionModel проверяет IsBusy и защищает всю операцию до применения ответа своим признаком занятости. Аудио и транскрибация продолжаются независимо.
- CancelAsync работает только при активной операции: отменяет её токен, физически закрывает WebSocket, ждёт завершения операции и reader; ConnectionLost запускает восстановление в SessionModel. Метод защищён SemaphoreSlim: повторные вызовы во время отмены пропускаются без очереди, дополнительно проверяется идентичность целевой операции. На время очистки IsBusy остаётся true. В простое CancelAsync ничего не делает. Прежний ResponseTimeout (2 минуты) сохранён; по его истечении или отмене вызывающим токеном незавершённая генерация также прерывается закрытием сокета, чтобы после снятия занятости не оставить скрытый параллельный запрос.
- Разрыв/таймаут/экстренная отмена/непригодная цепочка запускают реконнект с повторным warmup и свежей Session. Прерванный запрос НЕ повторяется; пользователь решает сам после сообщения о готовности. Подготовленные до восстановления запросы не посылаются в новую цепочку со старым саммари.
- Восстановленное саммари заменяет старое только в памяти; истории и саммари не сравниваются и не оптимизируются удалением ранних записей. Фрагменты, поступившие после отправленного снимка, остаются для следующих raw_records.
- Подключены сохранение и восстановление: TextProcessor реализует IReloadableTextProcessor. ProcessAsync добавляет фрагмент в память и буфер, затем пытается сохранить весь буфер через AddSessionMultipleDialogRecordsAsync. Метод IDatabase/SQLite атомарно добавляет весь пакет; AddSessionDialogRecordAsync сохранён в контракте, но рабочий процесс его не использует. ReloadAsync полностью заменяет _dialog объединением снимка GetSessionAsync и остатка буфера и сбрасывает _pendingMessage. Эти операции сериализованы общим SemaphoreSlim, поэтому записи во время перезагрузки ожидают её, а загрузка ожидает незавершённое сохранение. Ошибка чтения сохраняет прежнюю историю; ошибка записи логируется, а фрагменты остаются в памяти и буфере. При DisposeAsync выполняется последняя попытка сохранения.
- При ConnectionLost модель делает IsReady=false и запускает восстановление: connector.ReconnectAsync, DialogCoordinator.ReloadAsync, новая Session с инструкциями. Бывшие ответы отсекаются по ConnectionId и request_id. Новая Session и DialogRequest используют один сквозной счётчик request_id. Восстановление имеет максимум попыток и отменяется при Dispose; повторный разрыв во время завершающей стадии не оставляет ложное состояние Ready.
- Контроллер ожидает ProcessAsync, поэтому WaitForIdleAsync включает сохранение в БД. Время захвата теперь UTC; Local-время прямых вызовов процессора приводится к UTC согласно семантике SQLite. Синхронный Process оставлен для совместимости; в приложении используется асинхронный путь. Альтернативный SessionFileTextProcessor не менялся.
- Параметры: ChatGPTConnectorOptions — таймаут подключения 30 с и ответ 2 мин; SessionRecoveryOptions в core/DI — Delay 2 с и Attempts 3 (перенесены из настроек провайдера). ## Реализация SQLite

- Добавлен `aissyst.sqlite` в решение и ссылку тестового проекта. Зависит от core и `Microsoft.Data.Sqlite` 10.0.13. Core не зависит от SQLite.
- Публичный класс `aissyst.sqlite.SqliteDatabase(string databasePath)` реализует все методы `IDatabase`. Нужен путь к файлу; `:memory:` не поддерживается. Каталог и схема создаются лениво при первом обращении.
- Таблицы `contexts`, `context_blocks` (FK `context_id`), `sessions` (включая `name`, `creation_time`, инструкции, preview и `context` как JSON-массив), `dialog_records` (FK `session_id`, отдельный integer ID, `ts`, `role`, `message`). Сессия не связана FK с исходным контекстом.
- Foreign keys включены, WAL, индексы по `context_id` и `(session_id, ts)`, `PRAGMA user_version=1`. Неподдерживаемые версии отклоняются; миграций пока нет.
- Каждая операция открывает/закрывает соединение (pooling отключён). Операции одного экземпляра сериализуются `SemaphoreSlim`; SQL выполняется в `Task.Run`, поскольку провайдер синхронный. Все операции имеют транзакцию, чтение использует согласованный снимок.
- Даты хранятся как UTC ticks с точностью 100 нс. Local преобразуется в UTC, Unspecified трактуется как UTC. Возвращаемые даты имеют Kind=Utc. При одинаковых ts записи не теряются, внутренний ID разрешает равенство при чтении.
- ZIP разбирается целиком до вставки без распаковки на диск. Переносы в теле блока сохраняются, BOM поддерживается. Начальные инструкции/preview обязательны; прочие корневые файлы и вложенные блоки игнорируются.
- Сессия копирует контекст транзакционно. Исходные фрагменты добавляются отдельно или вся история заменяется атомарно. Источник Both для одной реплики отклоняется. Роли: Microphone→interviewee, Application→interviewer, None→unknown.
- Экспорт: GZip + UTF-8 JSON, `format_version`, `name`, `creation_time`, `instructions`, `preview`, `context` и `dialog`. ID не экспортируются. В целевой базе выдаётся новый локальный ID (численно может совпасть с ID в другой базе), время и имя сохраняются.
- Экспорт сначала пишет временный файл рядом с целевым, затем заменяет целевой файл. Импорт проверяет десериализацию, обязательные поля и версию до транзакции. Контекст в целевой базе не требуется.
- Отмена проверяется между этапами и записями, перед commit; уже выполняющийся SQL не прерывается. Ошибки не скрываются: отсутствие сущности — KeyNotFoundException, неверные архивы/JSON — InvalidDataException (некорректный UTF-8 — ошибка декодирования), ошибки SQLite передаются вызывающему коду.
- Добавлен английский `aissyst.sqlite/README.md`; обновлены корневой и Database README. `.gitignore` исключает SQLite-файлы/sidecar, но явно разрешает каталог проекта `aissyst.sqlite`.
- Подправлен устаревший тестовый `TestSessionDatabase` под текущий IDatabase (возвращаемый тип CreateSessionAsync и недостающие заглушки).

### Консольная инициализация сессии

- Дополнение по команде пользователя: после выбора номера сессии доступны `(o)open`, `(n)return to list`, `(d)delete`; для контекста — `(c)create new session`, `(n)return to list`, `(d)delete`. Клонирование сессий не предусмотрено.
- Удаление требует точного ввода `delete` (без изменения регистра или обрезки пробелов). Любой другой ответ возвращает к списку; EOF прекращает запуск. После возврата/удаления список перечитывается из БД, пустые списки переводят к следующему шагу.
- В `IDatabase` и SQLite добавлены `DeleteContextAsync(contextId, cancellationToken)` и `DeleteSessionAsync(sessionId, cancellationToken)`. Удаление транзакционное; отсутствующий ID вызывает `KeyNotFoundException`. Каскад удаляет блоки контекста или диалог сессии. Удаление контекста не затрагивает сессии.

- Реализован `aissyst.console/ConsoleSessionSelector.cs`: нумерованный список сессий с именем и UTC-временем, `Create New`, затем список контекстов и `Create from Template`.
- Пустой список сессий переводит к контекстам; пустой список контекстов — ко вводу пути ZIP. В обоих случаях выводится сообщение.
- Импорт шаблона сразу создаёт и выбирает сессию. Имя контекста берётся из имени архива. Пути с пробелами и обрамляющими одинарными/двойными кавычками поддерживаются.
- Неверные номера запрашиваются повторно. EOF прекращает запуск без выбранной сессии; Ctrl+C отменяет ввод через токен хоста. Ошибки выводятся в stderr, код завершения 1. После успешной инициализации повторный вызов сохраняет выбор.
- Импорт контекста и создание сессии — отдельные операции: при ошибке создания сессии импортированный контекст остаётся в БД (согласовано).

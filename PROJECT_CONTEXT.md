# Контекст проекта aissyst

Обновлено: 28 октября 2026 года. Реализация SQLite завершена по команде пользователя. Следующие изменения — по новой явной команде пользователя.

## Назначение и платформы

- Приложение помогает вести диалог: захватывает аудио, транскрибирует локально через Whisper и по запросу пользователя обращается к LLM за переводом, подсказкой или ответом.
- Два собеседника однозначно определяются источниками: микрофон — пользователь/экзаменуемый (`interviewee`), приложение — собеседник/экзаменатор (`interviewer`). Определение нескольких говорящих внутри источника сейчас не требуется.
- Текущая платформа — macOS; Windows предусмотрена архитектурой, её аудиозахват ещё не реализован. iOS в проекте нет.
- .NET 10, Generic Host, DI, R3. Кроссплатформенная координация находится в `aissyst.core`, консольный интерфейс — в `aissyst.console`.

## Аудио и транскрибация

- Источники непрерывно прослушиваются во время сессии. Начало аудиофрагмента определяется входным сигналом; тишина сама по себе запись не начинает.
- Завершение фрагмента: тишина, хоткей или достижение `MaxRecordingDuration`. Прослушивание после этого продолжается.
- Лимит считается по PCM-сэмплам с учётом частоты и числа каналов. Большой входной буфер делится с сохранением остатка для следующих фрагментов.
- В `ApplicationSettings` лимит по умолчанию 30 секунд; в текущем `Program.cs` явно установлено 15 секунд. Таймаут тишины — 1 секунда.
- `WhisperTranscriber` использует английскую `small.en-q5_1`; модель загружается при отсутствии в локальном кеше, проверяется SHA-256 и не хранится в Git.
- В `Program.cs` оба лимита обработки установлены в 1. Параллельную работу одного экземпляра Whisper не включать без отдельной проверки.
- Переполнение очередей удаляет самые старые ожидающие элементы с сообщением в журнале. Очистка очередей не отменяет уже выполняющуюся обработку.
- Источники публикуют аудиозаписи через R3; контроллер передаёт их в транскрибатор и текстовый процессор.
- `CaptureSession` создаётся в дочернем DI scope; уничтожение scope останавливает захват. После остановки перед сохранением текста ожидается завершение обработки оставшихся аудиофрагментов.

## Текстовый процессор и вывод

- Вместо текстовых кортежей используется immutable record `DialogMessage(Timestamp, Source, Text)`.
- `ITextProcessor.Process(DialogMessage)` синхронный, без `CancellationToken`. Возвращает законченную реплику или `null`.
- Фрагменты одного источника объединяются. Реплика считается законченной при поступлении непустого сообщения другого источника; пустой текст её не завершает.
- Незавершённая реплика доступна в истории, но не выводится как завершённая до смены источника.
- `GetDialog(fromTime)` возвращает снимок сообщений с `Timestamp > fromTime`, сортирует их по времени и объединяет соседние сообщения одного источника. Метка объединённой реплики соответствует последнему включённому фрагменту.
- `TextProcessor` восстанавливает историю выбранной сессии через `IDatabase.GetSessionAsync`. Роли `interviewer`/`interviewee` преобразуются в источники приложения/микрофона; прочие роли — в `None`.
- Восстановленные записи не выдаются повторно как новые законченные реплики. Контроллер отдельно выводит загруженную историю при запуске.
- `IOutput` отвечает за пользовательский вывод (`PrintDialogMessage`, `PrintLLMAnswer`); `ConsoleOutput` зарегистрирован в DI. Логгеры используются для служебных сообщений и ошибок.
- Дополнительный `SessionFileTextProcessor` находится в `aissyst.console`, не в core. Он сохраняет отдельные `microphone.txt` и `application.txt` в уникальной папке `transcripts/session-…` при завершении сессии. В файлах только текст одной строкой.
- `ISessionTextProcessor` удалён. Дополнительные методы файлового процессора вызываются напрямую из `MainThreadWorker` после приведения типа; контроллер предоставляет общее `WaitForIdleAsync`.
- Сейчас в DI выбран обычный `TextProcessor`, файловый процессор остаётся альтернативной реализацией.

## Сессия и LLM

- `ISessionSelector.InitializeAsync` выбирает сессию один раз. Затем модель и процессор синхронно получают её ID через `GetSelectedSessionId()`.
- Контроллер инициализирует селектор до модели/процессора. При подключённой модели она инициализирует процессор; отдельная перегрузка `InitializeAsync(sessionId, …)` удалена.
- `SessionModel` загружает вводную и тематический контекст из БД, получает восстановленный диалог из процессора и формирует `Session` для LLM.
- DTO описаны в `aissyst.core/LLMConnector/DTO`. `DTO-fields.txt` удалён пользователем в текущих изменениях; не восстанавливать автоматически. Пример начальных инструкций и протокола находится в `contexts/template/agent_initial_instructions.txt`.
- Пользователь унифицировал идентификатор: `Session`, `DialogRequest` и `DialogResponse` имеют поле `request_id` / свойство `RequestId`. Прежнее поле запроса `id` больше не актуально. `DialogRequest` также содержит `summary`, `raw_records` и тип запроса; ответ — `error`, `summary`, опциональный `summary_ts`, `message`.
- Саммари обновляется при каждом успешном ответе. В него входит состоявшийся диалог, но не сгенерированная подсказка, которую пользователь мог не произнести.
- `summary_ts` задаёт последнюю включённую в саммари реплику. Следующий запрос включает только сообщения с более поздней меткой. При пустом `raw_records` метка отсутствует; прежняя подтверждённая граница сохраняется.
- Для `summary_ts` добавлен nullable DateTime JSON-конвертер: отсутствие, JSON null и пустая/пробельная строка дают null; некорректная дата вызывает ошибку. При сериализации null поле опускается.
- Ответ проверяется относительно отправленного снимка. Не допускается смещение границы на ещё не отправленные сообщения или стирание существующего саммари пустым ответом.
- Актуальность ответов определяется `request_id`, а не только временем: разные запросы могут охватывать одинаковый диалог. Устаревшие и повторные ответы не применяются.
- Отправленный снимок не должен изменяться при продолжении той же реплики. Строгое чередование источников в списке не является обязательным условием.
- `md_format` разрешает Markdown только внутри ответного поля `message`, для удобства чтения пользователем. Входной контекст и `summary` не требуют Markdown.

## Хоткеи

Настраиваются в `ConsoleHotkeySettings`; при запуске выводится подсказка.

- Enter — начать прослушивание.
- Space — завершить текущие аудиофрагменты и продолжить прослушивание.
- S — остановить прослушивание.
- C — очистить ожидающие аудиозаписи и транскрипции с выводом количества удалённых элементов.
- Q / Ctrl+C — завершить приложение.
- 1 — перевод последней реплики собеседника на русский.
- 2 — подсказка для ответа на английском.
- 3 — полноценный ответ на английском.
- 4 — перевод и подсказка.
- 5 — перевод и полноценный ответ.

Запросы помощи доступны во время прослушивания и между сессиями записи. В режиме перенаправленного ввода после команды нужен Enter.

`ApplicationController.SendRequestAsync` выполняет запрос без блокирования чтения клавиатуры, обновляет модель и выводит ответ через `IOutput`. Новый запрос отменяет предыдущий; его поздний ответ не применяется даже при игнорировании отмены провайдером. Ошибки журналируются. Запросы LLM отслеживаются отдельно от обработки аудио: `WaitForIdleAsync` не ждёт их, а завершение контроллера отменяет и ожидает их.

`HostOptions.ShutdownTimeout` установлен пользователем в 3 секунды.

## Подключение ChatGPT: что реально готово

- Реализован вход Sign in with ChatGPT через системный браузер, loopback callback, PKCE и проверку ID-токена.
- Реальный вход в аккаунт успешно проверен; разрешение на использование плана получено. Повторный запуск использует сохранённую сессию без браузера.
- Секреты сохраняются вне репозитория; не читать и не выводить содержимое файлов учётных данных без необходимости. Токены и URL с ID token hint не журналировать.
- Реальная отправка контекста и запросов к модели **ещё не реализована**: `ChatGPTConnector.InitializeSession` и `SendRequest` пока возвращают `NotSupportedException`.
- Хоткеи, применение ответа, отмена и вывод проверены с тестовым коннектором, а не реальным inference-запросом.
- Пользователь подтвердил план: **Responses API через WebSocket с авторизацией Sign in with ChatGPT**. Под это обсуждались начальная отправка контекста и последующие запросы. HTTP со streaming был приведён ассистентом из документации, но не принят как изменение архитектуры. Не представлять выбор транспорта как открытый вопрос без новых оснований.
- WebSocket-транспорт ещё не реализован. При реализации проверить актуальную официальную документацию и ограничения SiWC; не считать, что авторизация сама обеспечивает хранение контекста. Локальная история нужна для восстановления после разрыва соединения.

## Хранение данных: последнее обсуждение

`IDatabase` реализован в отдельном проекте `aissyst.sqlite` (подробности ниже). `ISessionSelector` пока не реализован. В `Program.cs` база ещё не зарегистрирована: пользователь позже объяснит схему взаимодействия с пользователем. Полноценный запуск также требует реализации запросов LLM.

Прежняя идея JSON со ссылками на текстовые файлы заменена следующими решениями пользователя:

- База закрыта для ручного редактирования. Внешнее добавление данных — создание контекста из ZIP-шаблона и импорт ранее экспортированной сессии. Пользователь выбрал SQLite и подтвердил схему с четырьмя таблицами.
- `ContextInfo` содержит `Id` и `Name`. `SessionInfo` теперь содержит `Id`, `CreationTime` и `Name` (последний параметр по умолчанию пустой для совместимости старых вызовов). Новые сессии получают имя контекста + UTC-время создания, без ссылки на контекст.
- `ContextRecord` содержит `Topic` и `Body`; `SessionContext` — метаданные сессии, preview, блоки контекста и диалог; `DialogRecord` — время, роль, текст.
- Методы `IDatabase`: `GetContextsAsync`, `GetSessionsAsync`, `CreateContextAsync`, `CreateSessionAsync`, `GetSessionAsync`, `SetSessionDialogAsync`, `AddSessionDialogRecordAsync`, `ExportSessionAsync`, `ImportSessionAsync`, `GetSessionInitialInstructionsAsync`. Проверять актуальные сигнатуры в коде.

Шаблон контекста:

- ZIP, в корне обязательны `preview.txt`, `agent_initial_instructions.txt` и каталог `context/`. Дополнительной внешней папки вокруг них быть не должно.
- UTF-8, обычный текст. Начальные инструкции передаются LLM до `Session`.
- Каждый `.txt` непосредственно в `context/` — тематический блок: первая строка — заголовок, остальное — тело с сохранением внутренних переносов. Заголовок непустой, тело может быть пустым.
- Имена блоков произвольны. Нумерация и порядок блоков не имеют договорного значения. Не навязывать префиксы или дополнительное упорядочивание.
- Вложенные каталоги и дополнительные служебные файлы в корне не читаются.
- `CreateContextAsync` получает путь к ZIP и необязательное имя. При отсутствии/пробельном имени используется имя архива без расширения. Контекст получает уникальный ID, имя не является идентификатором.
- В `contexts/template` пользователь подготовил развёрнутый пример: 68 блоков, у всех есть заголовки; 47, 48, 64 и 65 имеют пустое тело. `EMPTY_BLOCKS.txt` — служебная памятка, игнорируется при импорте. Шаблон содержит персональные сведения: не дублировать их без необходимости в документации.
- Пользователь добавил `request_id` в начальные инструкции и примеры. Оставшаяся небольшая несогласованность: текст примеров всё ещё говорит «Все четыре поля», хотя полей пять. Шаблон ассистент не менял.

Сессии и переносимость:

- При создании сессии preview, инструкции и блоки контекста полностью копируются. Копия неизменна всю жизнь сессии. Сессия **не знает об исходном контексте как отдельной сущности** и не зависит от его наличия.
- `GetSessionInitialInstructionsAsync` возвращает персональную копию инструкций конкретной сессии.
- Пользователь согласился сохранять исходные фрагменты транскрипции. Порядок определяется временными метками; дополнительную нумерацию/порядковый ключ сейчас не вводить. `SetSessionDialogAsync` оставлен для полной замены истории, `AddSessionDialogRecordAsync` — добавление фрагмента.
- Экспорт содержит все данные сессии, включая инструкции и контекст, и не предназначен для ручного редактирования. Реализован GZip-сжатый JSON (`.json.gz`), версия формата 1.
- Формат имеет версию; пока достаточно точного совпадения версий без обратной совместимости. Импорт выдаёт новый ID в целевой базе.
- Пользователь считает достаточным прочитать файл целиком и десериализовать до записи в БД; потоковая обработка и запрет распаковки на диск не нужны. Обсуждён минимальный контроль обязательных полей/ненулевого результата и версии, поскольку обычная десериализация может принять `{}`. Сложный валидатор не требовался.
- Создание/импорт сохраняют готовый объект атомарно после разбора; не оставляют частичные записи.

## Реализация SQLite

- Добавлен `aissyst.sqlite` в решение и ссылку тестового проекта. Зависит от core и `Microsoft.Data.Sqlite` 10.0.13. Core не зависит от SQLite.
- Публичный класс `aissyst.sqlite.SqliteDatabase(string databasePath)` реализует все методы `IDatabase`. Нужен путь к файлу; `:memory:` не поддерживается. Каталог и схема создаются лениво при первом обращении.
- Таблицы `contexts`, `context_blocks` (FK `context_id`), `sessions` (включая `name`, `creation_time`, инструкции, preview и `context` как JSON-массив), `dialog_records` (FK `session_id`, отдельный integer ID, `ts`, `role`, `message`). Сессия не связана FK с исходным контекстом.
- Foreign keys включены, WAL, индексы по `context_id` и `(session_id, ts)`, `PRAGMA user_version=1`. Неподдерживаемые версии отклоняются; миграций пока нет.
- Каждая операция открывает/закрывает соединение (pooling отключён). Операции одного экземпляра сериализуются `SemaphoreSlim`; SQL выполняется в `Task.Run`, поскольку провайдер синхронный. Все операции имеют транзакцию, чтение использует согласованный снимок.
- Даты хранятся как UTC ticks с точностью 100 нс. Local преобразуется в UTC, Unspecified трактуется как UTC. Возвращаемые даты имеют Kind=Utc. При одинаковых ts записи не теряются, внутренний ID разрешает равенство при чтении.
- ZIP разбирается целиком до вставки без распаковки на диск. Переносы в теле блока сохраняются, BOM поддерживается. Начальные инструкции/preview обязательны; прочие корневые файлы и вложенные блоки игнорируются.
- Сессия копирует контекст транзакционно. Исходные фрагменты добавляются отдельно или вся история заменяется атомарно. Источник Both для одной реплики отклоняется. Роли: Microphone→interviewee, Application→interviewer, None→unknown.
- Экспорт: GZip + UTF-8 JSON, `format_version`, `name`, `creation_time`, `instructions`, `preview`, `context` и `dialog`. ID не экспортируются. В целевой базе выдаётся новый локальный ID (численно может совпасть с ID в другой базе), время и имя сохраняются.
- Экспорт сначала пишет временный файл рядом с целевым, затем заменяет целевой файл. Импорт проверяет десериализацию, обязательные поля и версию до транзакции. Контекст в целевой базе не требуется.
- Отмена проверяется между этапами и записями, перед commit; уже выполняющийся SQL не прерывается. Ошибки не скрываются: отсутствие сущности — KeyNotFoundException, неверные архивы/JSON — InvalidDataException (некорректный UTF-8 — ошибка декодирования), ошибки SQLite передаются вызывающему коду.
- Добавлен английский `aissyst.sqlite/README.md`; обновлены корневой и Database README. `.gitignore` исключает SQLite-файлы/sidecar, но явно разрешает каталог проекта `aissyst.sqlite`.
- Подправлен устаревший тестовый `TestSessionDatabase` под текущий IDatabase (возвращаемый тип CreateSessionAsync и недостающие заглушки).
- В консоль база не подключалась, UI выбора сессии не реализовывался: пользователь отдельно опишет желаемое взаимодействие. Модель и передача LLM не менялись.

Следующий этап — пользовательская схема взаимодействия/выбора сессии и подключение хранилища к приложению. Не начинать автоматически без команды пользователя.

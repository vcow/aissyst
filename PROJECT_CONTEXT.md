# Контекст проекта aissyst

Обновлено: 31 октября 2026 года. В aissyst.desktop реализован независимый стартовый визард через сервис: сессия/контекст/ZIP, модель и reasoning effort, микрофон и приложение. Удаление с подтверждением доступно и для сессий, и для контекстов. Журнал и визард показываются как независимые окна рядом; пользовательское закрытие визарда заблокировано, успешный запуск закрывает его программно. Подключены общий ApplicationController, OAuth/ChatGPT, Whisper, SQLite и SessionModel; логи общих ILogger<T> направлены в журнал. GUI инициализирует LLM-сессию, но пока не начинает аудиозахват и не имеет кнопок подсказок. Консоль остаётся полным рабочим интерфейсом. Визард показывает реальный прогресс скачивания Whisper и этапы запуска через отдельный канал IProgress. Журнал переведён на ListBox с фильтрами, Copy/Clear, цветами и управляемой автопрокруткой; ограничение хранения снято по решению пользователя. Добавлены меню приложения и модальные настройки всех свойств IApplicationSettings; настройки desktop сохраняются отдельно и применяются при следующем запуске, закрытие журнала больше не завершает процесс. Полный прогон — 306 тестов; реальный вход/LLM через GUI проверяет пользователь.

## Назначение и платформы

- Приложение помогает вести диалог: захватывает аудио, транскрибирует локально через Whisper и по запросу пользователя обращается к LLM за переводом, подсказкой или ответом.
- Два собеседника однозначно определяются источниками: микрофон — пользователь/экзаменуемый (`interviewee`), приложение — собеседник/экзаменатор (`interviewer`). Определение нескольких говорящих внутри источника сейчас не требуется.
- Текущая платформа — macOS; Windows предусмотрена архитектурой, её аудиозахват ещё не реализован. iOS в проекте нет.
- .NET 10, Generic Host, DI. Кроссплатформенная координация находится в `aissyst.core`, консольный интерфейс — в `aissyst.console`. Базовый оконный проект — `aissyst.desktop`.

## Базовый оконный проект

- По команде пользователя добавлен один проект `aissyst.desktop` в `aissyst.sln`. Avalonia, Avalonia.Desktop и Avalonia.Themes.Fluent закреплены на версии 12.1.4; TargetFramework — net10.0, OutputType — WinExe.
- `Program.BuildAvaloniaApp` настраивает платформу и трассировку; `App.axaml` подключает FluentTheme и системный вариант темы. `Views/MainWindow.axaml` — окно журнала: виртуализированный ListBox на фоне #1E1E1E, одна структурированная LogEntry на сообщение с многострочным исключением. Текст Info белый, Warning жёлтый, Error/Critical красный; SelectableTextBlock сохраняет выделение фрагментов. Независимые toggle Info/Warning/Error (все включены, Critical в Error) фильтруют только показ. Copy копирует весь снимок накопленного журнала, включая скрытые и ещё не отрисованные записи; сборка строки выполняется в фоне. Clear очищает весь журнал и очередь ожидающих показа записей, сохраняя фильтры и приём новых сообщений. По явному решению пользователя лимит 200 000 символов удалён, автоматического усечения нет; журнал хранится в памяти до Clear/выхода. LogViewModel принимает записи потокобезопасно и добавляет их в UI пакетами с одним уведомлением на пакет; фильтр перестраивает видимую коллекцию, не уничтожая оригиналы.
- `WindowLoggerProvider` реализует ILoggerProvider и зарегистрирован через AddLogging в общем desktop DI. ILogger<ApplicationController>, логгеры Whisper, SessionModel, ChatGPTConnector и остальных сервисов используют его; общий ILogger<T> и консольный провайдер не менялись. Уровень Information и выше, время, категория, уровень и полное исключение сохраняются отдельно в LogEntry, строки лога не парсятся. Автопрокрутка следует за последними видимыми записями; прокрутка вверх останавливает её, новые сообщения не сдвигают позицию чтения. Кнопка Latest появляется при остановке и возвращает к последней записи, возобновляя слежение; ручная прокрутка в конец также возобновляет его. ListBox использует собственный ScrollViewer и VirtualizingStackPanel. Диагностика Avalonia остаётся в LogToTrace.
- Используется classic desktop lifetime и ShutdownMode.OnExplicitShutdown. DesktopApplicationShell задаёт нативные меню Application/Dock на macOS: Settings… первым, затем Show Log и Quit; Cmd+, / Cmd+Q, Application.Name=aissyst, стандартные пункты Avalonia отключены, ShowInDock=true. На остальных платформах есть Application-меню в журнале. На macOS Close журнала отменяется и окно скрывается, setup и сервисы продолжают работу; Show Log/активация Dock Reopen возвращают тот же журнал. На остальных платформах Close сворачивает журнал, оставляя доступ через taskbar. Реальное завершение — только Quit/системный запрос; shell разрешает закрытие окна лишь после освобождения сервисов. Повторное Opened не запускает setup повторно. Конкретные окна диалога и подсказок ещё не реализованы.
- Исправлено отображение одного About Avalonia вместо меню приложения: в Avalonia 12.1.4 macOS экспортёр создаётся в AppBuilder.AfterSetup до OnFrameworkInitializationCompleted и получает текущий NativeMenu один раз. Прежний shell поздно заменял корневой объект, нативная строка сохраняла прежнее fallback-меню. Теперь NativeMenu объявлен в App.axaml и создаётся в App.Initialize; DesktopApplicationShell заполняет тот же экземпляр с сохранением Parent нативного контейнера. Dock получает отдельное меню. Тестовый MenuStartupProbe захватывает корень в AfterSetup, до настройки shell, затем проверяет сохранность экземпляра/Parent и вызывает Settings, Show Log и Quit через INativeMenuItemExporterEventsImplBridge, как нативный экспортёр. Причина сверена с исходниками Avalonia тега 12.1.4; реальное отображение Cocoa ассистентом не запускалось.
- `DesktopServices.Create` возвращает ServiceCollection с общими сервисами, GUI-селекторами и оконным провайдером журнала; опционально принимает DesktopSettingsStore для изолированных тестов. Ссылки desktop на console нет. По замечанию пользователя перенос ApplicationSettings в core отменён: исходный класс и значения/валидация восстановлены в aissyst.console; в core остаётся IApplicationSettings. Desktop использует собственный DesktopApplicationSettings : IApplicationSettings и DesktopSettingsStore. Общие сервисы получают неизменяемый Active-снимок при запуске. В console явно добавлен стандартный AddConsole; ILogger<T> и консольный сценарий сохранены.
- App ставит запуск ApplicationController.InitializeAsync в очередь UI с приоритетом ApplicationIdle после Opened окна журнала; работа контроллера выполняется в фоне. Существующий порядок сохранён: выбор сессии → OAuth и модель/effort → Whisper → восстановление диалога и настоящая LLM-сессия → выбор аудио. После успеха журнал сообщает о готовности и визард закрывается; аудио не стартует. Ошибка логируется и показывается в остающемся открытым визарде с остановленным индикатором ожидания. При выборе Quit/системном запросе завершения отменяется запуск, закрывается модальный Settings (с ожиданием текущего сохранения), ожидается его завершение и асинхронное освобождение DI (включая программное закрытие визарда), затем завершается Avalonia. GUI использует ту же БД и OAuth-хранилище, что console; из-за эксклюзивной блокировки хранилища следует запускать один интерфейс за раз.
- Запуск: `dotnet run --project aissyst.desktop/aissyst.desktop.csproj`. Пользователь уточнит внешний вид и организацию окон перед дальнейшей реализацией. README проекта на английском описывает состав и текущие границы готовности.
- `IWizardService.ShowAsync(WizardPage, ct)` — общий независимый UI-контракт, возвращает ключ выбранного варианта либо путь ZIP. WizardService создаёт одно независимое немодальное окно по первому запросу, сериализует запросы SemaphoreSlim и обновляет UI через Dispatcher. Прежний Show(owner)/CenterOwner заменён на Show() и DesktopWindowPlacement: оба окна располагаются рядом в рабочей области текущего монитора, визард имеет фиксированный размер 620 × 520 логических пикселей (CanResize=false и совпадающие Min/Max), при необходимости уменьшается только ширина журнала. Журнал остаётся видимым и доступным; родительской связи между окнами нет. Нет ID окна в селекторах. RadioButton-список в ScrollViewer, Next подтверждает только текущий запрос и сразу деактивируется; Previous нет. Между запросами окно сохраняет страницу с отключённым вводом и индикатором ожидания. Явный CompleteAsync из App после успешного InitializeAsync закрывает окно без признака последнего шага в селекторах. WizardWindow использует WindowDecorations.BorderOnly без активных нативных кнопок закрытия/сворачивания/разворачивания, перетаскивается за отдельную постоянную полосу «aissyst - Setup» высотой 36 пикселей, доступную при ожидании и ошибке; OnClosing отклоняет обычные попытки закрытия, разрешая их только через внутренний Complete. При ошибке FailAsync оставляет окно открытым с сообщением, без бесконечного прогресса. Dispose при завершении всего приложения отменяет ожидающий запрос, программно закрывает окно и ждёт освобождения gate.
- DesktopSessionSelector выбирает существующую сессию или создаёт новую из контекста/ZIP. Для сохранённой сессии на той же странице доступны Delete и Next (Open), для Create New — обычная Next. Для сохранённого контекста — Delete и Next (Create), для Create from Template — обычная Next. WizardOption содержит подпись основной кнопки и необязательный WizardAction (ключ результата, подпись и текст подтверждения); окно остаётся независимым от сущностей. Delete показывает встроенное подтверждение, блокирует смену выбранного пункта и предлагает Confirm Delete / Cancel. Cancel не завершает запрос селектора. После подтверждения обе кнопки блокируются, селектор удаляет сущность через существующие IDatabase.DeleteSessionAsync/DeleteContextAsync и перечитывает соответствующий список. При удалении последней сессии открывается выбор контекста; после последнего контекста — импорт ZIP. Ошибка удаления выводится на той же странице и логируется. Удаление контекста сохраняет уже созданные из него сессии. Пользователь уточнил, что консоль работает корректно; при доработках действий и окон она не менялась. Для ZIP есть редактируемый путь и системный picker; ошибка импорта позволяет исправить файл на той же странице. DesktopModelSelector использует каталог аккаунта, предлагает server default и известные уровни, подставляет catalog default; при отсутствии уровней лишней страницы нет. Выбор модели коммитится только после effort. DesktopCaptureSession выбирает разрешённые источники, разрешает None для каждого, но повторяет выбор с ошибкой при отсутствии обоих. Выбор не начинает захват; передача реальных аудиофрагментов и рабочие элементы управления — следующий этап.
- Пользователь повторно потребовал начинать реализацию исходного кода только по прямой команде приступить к реализации. Правило уточнено в AGENTS.md. Этот этап реализации явно разрешён сообщением «Можешь приступать к реализации визарда»; последующее указание оставить журнал в покое ограничило изменения подключением ILogger к уже имеющемуся компоненту. Последующая явная команда «Можешь приступать к выполнению» разрешила доработку самого журнала: ListBox, фильтры, Copy/Clear, цвета и управляемая автопрокрутка, без лимита хранения. Позднее пользователь прямо поручил добавить меню и модальное Settings со всеми настройками IApplicationSettings, возвратом к defaults и раздельными реализациями настроек интерфейсов.


- Settings — отдельный SettingsWindow/SettingsViewModel через DesktopSettingsDialog, один экземпляр, ShowDialog с владельцем-журналом; существующие и вновь открываемые окна (включая визард) временно отключены. Форма содержит General (dropdown Both/Microphone/Application, Markdown), Recording (числовые секунды тишины и максимального фрагмента, порог 0–1), Processing (ёмкость очереди, два целочисленных слайдера 1–5), Transcription (путь модели с Browse, URL, SHA-256, язык). Прежние рабочие defaults сохранены: Both, 1 с тишины, 15 с фрагмент, 0.01, очередь 10, лимиты 1/1, en, Markdown=true, прежние модель/URL/хеш. Консольный конструктор по-прежнему имеет MaxRecordingDuration=30 с, Program явно задаёт 15 с.
- Save валидирует все поля, атомарно пишет UTF-8 JSON с читаемым Unicode в LocalApplicationData/aissyst/desktop-settings.json и закрывает форму; ошибка остаётся в форме и журнале. Cancel/X ничего не сохраняет; Restore Defaults заполняет форму, сохранение требует Save. Настройки применяются при следующем запуске; это явно указано в окне. Runtime Active не меняется после сохранения, Saved используется при повторном открытии формы. Невалидный JSON/значения дают warning и defaults без автоматического перезаписывания повреждённого файла. Докачка/сеть не вызываются из окна Settings. Лимиты обработки выше 1 разрешены, но WhisperTranscriber по-прежнему сериализует нативную обработку через _lifecycle.

## Аудио и транскрибация

- Источники непрерывно прослушиваются во время сессии. Начало аудиофрагмента определяется входным сигналом; тишина сама по себе запись не начинает.
- Завершение фрагмента: тишина, хоткей или достижение `MaxRecordingDuration`. Прослушивание после этого продолжается.
- Лимит считается по PCM-сэмплам с учётом частоты и числа каналов. Большой входной буфер делится с сохранением остатка для следующих фрагментов.
- В `ApplicationSettings` лимит по умолчанию 30 секунд; в текущем `Program.cs` явно установлено 15 секунд. Таймаут тишины — 1 секунда.
- `WhisperTranscriber` использует английскую `small.en-q5_1`; модель загружается при отсутствии в локальном кеше, проверяется SHA-256 и не хранится в Git.
- По команде «Да, действуй» периодическое логирование загрузки заменено реальным прогрессом визарда. Общий InitializationProgress (сообщение, полученные и ожидаемые байты) передаётся через необязательный IProgress в WhisperTranscriber и ApplicationController; DesktopStartupProgress переводит его в независимый WizardService.ReportProgress. При известном Content-Length показаны процент и полученный/общий объём в десятичных МБ, при неизвестном — полученный объём и индикатор ожидания. Подключение к серверу загрузки, проверка SHA-256, нативная загрузка модели, восстановление диалога/подключение LLM и перечисление аудиоисточников показывают название этапа. Счётчик обновляется по первым/последним байтам и не чаще чем раз в 200 мс между ними. Сервис объединяет ожидающие обновления в один UI callback; смена страницы, ошибка и завершение отбрасывают накопленный прогресс прежней страницы. ILogger не парсится; компонент журнала не оптимизировался. В обычном журнале остаются начало, завершение, отмена и ошибки, HTTP-метаданные/безопасные URL/временный путь перенесены на Debug; PeriodicTimer удалён. Контрольная сумма, атомарная замена, очистка частичного файла, URL, таймауты и расположение кеша сохранены, повторные попытки и докачка не добавлялись. Консоль использует прежние конструкторы без подписчика прогресса и сохраняет журнал основных событий.
- Пользовательский лог установил реальную причину сбоя загрузки: неожиданное закрытие TLS-потока (IOException / unexpected EOF) после 227,6 с и 153 776 729 из 190 098 681 байта (~81%); это не таймаут. Частичный файл удалён штатно. Пользователь решил оставить механизм скачивания как есть, поскольку он нужен при первом старте, и заменить подробный прогресс в журнале показом в визарде. Предварительно в консольном каталоге обнаружена исправная модель 181 МБ с ожидаемым SHA-256, desktop использует собственный каталог. Файл модели ассистент не копировал, полную сетевую загрузку не запускал.
- В `Program.cs` оба лимита обработки установлены в 1. Параллельную работу одного экземпляра Whisper не включать без отдельной проверки.
- Переполнение очередей удаляет самые старые ожидающие элементы с сообщением в журнале. Очистка очередей не отменяет уже выполняющуюся обработку.
- По решению пользователя совпадения временных меток транскрипций считаются допустимым редким риском для текущего сценария. При отказе SortedSet добавить сообщение с уже имеющейся меткой контроллер пишет Warning с временем и источником, без текста транскрипции. Поведение очереди и DTO не менять ради этого случая; вопрос закрыт этим предупреждением.
- `ICaptureSession` публикует аудиозаписи через события `MicrophoneRecordingCompleted` и `ApplicationRecordingCompleted` с `IReadOnlyList<AudioFrame>`; контроллер передаёт их в транскрибатор и текстовый процессор. При завершении контроллер явно отписывается от событий, ожидает задачи и освобождает семафоры/источник отмены. `ConsoleCaptureSession.Dispose` очищает обработчики. Пакет R3 и его типы удалены из исходников.
- `CaptureSession` создаётся в дочернем DI scope; уничтожение scope останавливает захват. После остановки перед сохранением текста ожидается завершение обработки оставшихся аудиофрагментов.
- `CaptureSession.PauseAndCompleteRecordingsAsync` ставит Complete в общую очередь, публикует незавершённые фрагменты обоих источников и приостанавливает чтение очереди, возвращая IDisposable для возобновления. Источники продолжают складывать кадры в канал; таймер при паузе пропускает события. Канал ограничен 512 событиями, FullMode.Wait: при заполнении логируется Warning о задержке производителей и риске переполнения буферов источников. Повторные предупреждения подавляются до разгрузки ниже половины ёмкости. Это не режим удаления кадров. Dispose сессии отменяет паузу и дообрабатывает накопленные события; отменённая до подтверждения команда паузы не оставляет захват остановленным.
- Обычный `CompleteRecordingsAsync` только завершает фрагменты, без паузы. Space и запросы помощи во время прослушивания используют PauseAndCompleteRecordingsAsync. Граница соответствует позиции Complete в очереди; неподанные источниками кадры в неё не входят.

## Текстовый процессор и вывод

- Вместо текстовых кортежей используется immutable record `DialogMessage(Timestamp, Source, Text)`.
- `ITextProcessor.Process(DialogMessage)` сохранён как синхронный совместимый метод. Контроллер использует `ProcessAsync(message, cancellationToken)` и ожидает сохранение в БД. Возвращается законченная реплика или `null`.
- Исходные фрагменты всегда добавляются в буфер несохранённых записей и историю памяти без обрезки пробелов/переносов и без объединения (включая пустые). Каждая новая запись запускает попытку сохранить весь буфер одной транзакцией; только успех очищает буфер. Ошибка БД логируется и не мешает фиксации фрагмента в памяти. В памяти также хранятся исходные тексты; представление реплик нормализуется при обработке и чтении. Метки времени согласованы с SQLite как UTC.
- Фрагменты одного источника объединяются. Реплика считается законченной при поступлении непустого сообщения другого источника; пустой текст её не завершает.
- Незавершённая реплика доступна в истории; автоматический вывод срабатывает при смене источника. По Space она показывается сразу, без искусственной смены говорящего или изменения диалога. Контроллер хранит показанные объединённые реплики и дописывает только новые реплики либо продолжение уже показанной. Для автоматического завершения сравнивается снимок истории до временной метки завершённой реплики, чтобы не терять повторяющиеся слова после восстановления и не дублировать уже показанные фрагменты. Space не вызывает Clear и сохраняет ответы LLM и служебный вывод.
- `GetDialog(fromTime)` возвращает снимок сообщений с `Timestamp > fromTime`, сортирует их по времени и объединяет соседние сообщения одного источника. Метка объединённой реплики соответствует последнему включённому фрагменту.
- `TextProcessor` восстанавливает историю выбранной сессии через `IDatabase.GetSessionAsync`. Роли `interviewer`/`interviewee` преобразуются в источники приложения/микрофона; прочие роли — в `None`.
- Восстановленные записи не выдаются повторно как новые законченные реплики. Контроллер очищает отображение и пакетно выводит полную историю при запуске и реконнекте, включая незавершённую реплику.
- `IOutput` отвечает за пользовательский вывод (`Clear`, `PrintMultipleDialogMessages`, `PrintDialogMessage`, `PrintLLMAnswer`); `ConsoleOutput` зарегистрирован в DI. Логгеры используются для служебных сообщений и ошибок.
- Дополнительный `SessionFileTextProcessor` находится в `aissyst.console`, не в core. Он сохраняет отдельные `microphone.txt` и `application.txt` в уникальной папке `transcripts/session-…` при завершении сессии. В файлах только текст одной строкой.
- `ISessionTextProcessor` удалён. Дополнительные методы файлового процессора вызываются напрямую из `MainThreadWorker` после приведения типа; контроллер предоставляет общее `WaitForIdleAsync`.
- Сейчас в DI выбран обычный `TextProcessor`, файловый процессор остаётся альтернативной реализацией.

## Сессия и LLM

- `ISessionSelector.InitializeAsync` выбирает сессию один раз. Затем модель и процессор синхронно получают её ID через `GetSelectedSessionId()`.
- Контроллер инициализирует селектор до модели/процессора. При подключённой модели она инициализирует процессор; отдельная перегрузка `InitializeAsync(sessionId, …)` удалена.
- `SessionModel` загружает вводную и тематический контекст из БД, получает восстановленный диалог из процессора и формирует `Session` для LLM.
- DTO описаны в `aissyst.core/LLMConnector/DTO`. `DTO-fields.txt` удалён пользователем в текущих изменениях; не восстанавливать автоматически. Пример начальных инструкций и протокола находится в `contexts/template/agent_initial_instructions.txt`.
- Пользователь унифицировал идентификатор: `Session`, `DialogRequest` и `DialogResponse` имеют поле `request_id` / свойство `RequestId`. Прежнее поле запроса `id` больше не актуально. `DialogRequest` также содержит `summary`, `raw_records` и тип запроса; ответ — `error`, `summary`, опциональный `summary_ts`, `message`.
- Саммари обновляется при каждом успешном ответе. В него входит состоявшийся диалог, но не сгенерированная подсказка, которую пользователь мог не произнести.
- `summary_ts` задаёт последнюю включённую в саммари реплику. Следующий запрос включает только сообщения с более поздней меткой. При пустом `raw_records` метка отсутствует; прежняя подтверждённая граница сохраняется.
- Для `summary_ts` добавлен nullable DateTime JSON-конвертер: отсутствие, JSON null и пустая/пробельная строка дают null; некорректная дата вызывает ошибку. При сериализации null поле опускается.
- Ответ проверяется относительно отправленного снимка. Не допускается смещение границы на ещё не отправленные сообщения или стирание существующего саммари пустым ответом.
- Актуальность ответов определяется `request_id`, а не только временем: разные запросы могут охватывать одинаковый диалог. Устаревшие и повторные ответы не применяются.
- Отправленный снимок не должен изменяться при продолжении той же реплики. Строгое чередование источников в списке не является обязательным условием.
- `md_format` разрешает Markdown только внутри ответного поля `message`, для удобства чтения пользователем. Входной контекст и `summary` не требуют Markdown.

## Хоткеи

Настраиваются в `ConsoleHotkeySettings`; при запуске выводится подсказка.

- Enter — начать прослушивание.
- Space — завершить аудиофрагменты, дождаться транскрибации и показать весь текущий диалог с последней репликой; продолжить прослушивание.
- S — остановить прослушивание.
- C — очистить ожидающие аудиозаписи и транскрипции с выводом количества удалённых элементов.
- Q / Ctrl+C — завершить приложение.
- 1 — перевод последней реплики собеседника на русский.
- 2 — подсказка для ответа на английском.
- 3 — полноценный ответ на английском.
- 4 — перевод и подсказка.
- 5 — перевод и полноценный ответ.

Запросы помощи доступны во время прослушивания и между сессиями записи. В режиме перенаправленного ввода после команды нужен Enter.

`ApplicationController.ShowDialogAsync` — отдельная операция вывода по Space, без LLM. MainThreadWorker запускает её в фоне, передавая session.PauseAndCompleteRecordingsAsync. Контроллер ждёт WaitForIdleAsync и вызывает DialogCoordinator.ShowHistoryAsync: под общим gate снимается история из памяти и публикуется отдельное событие HistoryRequested для пакетного добавления непоказанного текста без Clear. HistoryReplaced оставлено для восстановления с полной заменой отображения. БД не перечитывается, граница саммари и request_id не меняются. IDisposable паузы освобождается в finally. Операции показа отслеживаются отдельно от транскрибации, чтобы WaitForIdleAsync не ждал сам себя; при уничтожении контроллера они отменяются и ожидаются. S/Q/Ctrl+C доступны во время ожидания; повторные Space последовательно обрабатываются через очередь Complete.

`ApplicationController.SendRequestAsync` выполняет запрос без блокирования чтения клавиатуры, обновляет модель и выводит ответ через `IOutput`. При активном захвате MainThreadWorker передаёт callback pauseAudioProcessing = session.PauseAndCompleteRecordingsAsync; контроллер занимает запрос до начала подготовки, получает паузу, ждёт WaitForIdleAsync и синхронно вызывает SessionModel.SendRequestAsync для снимка диалога. IDisposable паузы освобождается в finally сразу после формирования запроса, до ожидания ответа LLM, также при ошибке/отмене. При молчании ожидание не требует нового текста. Без активного захвата callback отсутствует, ожидаются оставшиеся задачи обработки. Новый запрос во время подготовки или при занятом коннекторе отклоняется с InvalidOperationException. Одновременно выполняется один LLM-запрос, без очереди. Принимается корректный успешный ответ с request_id выше последнего принятого; ошибочный ответ границу не меняет, устаревшие ID игнорируются. Ошибки журналируются. Запросы LLM отслеживаются отдельно от обработки аудио: WaitForIdleAsync не ждёт их, а завершение контроллера отменяет и ожидает их.

`HostOptions.ShutdownTimeout` установлен пользователем в 3 секунды.

## Подключение ChatGPT: что реально готово

- Реализован вход Sign in with ChatGPT через системный браузер, loopback callback, PKCE и проверку ID-токена.
- Реальный вход в аккаунт успешно проверен; разрешение на использование плана получено. Повторный запуск использует сохранённую сессию без браузера.
- Секреты сохраняются вне репозитория; не читать и не выводить содержимое файлов учётных данных без необходимости. Токены и URL с ID token hint не журналировать.
- Новый реальный запуск без stream_id прошёл warmup, но при разборе ответа на Session извлечённый output_text был пустым; прежний парсер падал на JsonDocument.Parse пустой строки. Теперь он выдаёт InvalidDataException с response ID и status. Последующий полный лог установил причину: response.output_item.done содержит корректный DialogResponse, а response.completed.output пуст. Исправлено сохранением завершённых элементов в Pending до успешного response.completed. Пользователь явно разрешил временно расширить логирование вплоть до полного текста для LLM: добавлена опция ChatGPTConnectorOptions.LogProtocolPayloads (по умолчанию false), в консольном Program.cs она временно включалась для диагностики, а после успешного пользовательского запуска отключена (используется значение false по умолчанию). При включённой опции на Information выводятся полные исходящие/входящие JSON-сообщения WebSocket с метками SEND/RECEIVE, включая инструкции и контекст; HTTP-заголовки авторизации не выводятся. В обычном запуске подробные SEND/RECEIVE не выводятся; готовые ответы и сообщения об ошибках сохранены. Формат запросов и алгоритм инициализации не менялись.
- Первый реальный запуск дошёл до WebSocket, но сервер отклонил warmup с HTTP 400; точная причина в прежнем логе была потеряна. `ResponsesApiException` теперь сохраняет status/code/type/message/param/request_id, включая ошибки без code и с detail. Транспорт журналирует их вместе с моделью, типом события и response ID; response.failed и response.incomplete сохраняют серверную причину. В обычном режиме полные исходящие запросы и заголовки авторизации не выводятся; временная диагностика полного JSON описана выше. Повторный лог выявил Unsupported parameter: stream_id. Два разрешённых пользователем минимальных реальных запроса к gpt-6.1-sol подтвердили: с stream_id — HTTP 400, без него — response.completed и OK (14 токенов). Проверка выполнена отдельным скриптом в /private/tmp/aissyst-ws-probe, без персонального контекста. Последующий пользовательский лог подтвердил warmup и генерацию Session по JSON-схеме; сборка результата исправлена после обнаружения пустого терминального output. Последующий log.txt подтвердил успешный запрос reply с request_id=2 по previous_response_id, один завершённый ответ и его однократный пользовательский вывод; 416 deltas были диагностическими событиями той же генерации.
- `ChatGPTConnector.InitializeSession` и `SendRequest` реализованы через Responses API WebSocket; подробности и границы проверки ниже.
- Пользовательский запуск подтвердил запрос reply по хоткею 3, применение и однократный вывод реального ответа. Остальные типы помощи и отмена пока проверены автоматическими тестами; пользователь переходит к оценке работоспособности приложения.
- Пользователь подтвердил план: **Responses API через WebSocket с авторизацией Sign in with ChatGPT**. Под это обсуждались начальная отправка контекста и последующие запросы. HTTP со streaming был приведён ассистентом из документации, но не принят как изменение архитектуры. Не представлять выбор транспорта как открытый вопрос без новых оснований.
- WebSocket-транспорт реализован по текущей официальной документации и ограничениям SiWC. Авторизация не обеспечивает постоянное хранение контекста; восстановление использует локальную историю.

### WebSocket-коннектор: текущая реализация

- Исходящие инструкции, DTO Session/DialogRequest и внешние события response.create используют общий ResponsesProtocol.Serialize с JavaScriptEncoder.UnsafeRelaxedJsonEscaping. Кириллица передаётся буквами в UTF-8 на обоих уровнях JSON; кавычки, обратные слеши и управляющие символы сохраняют обязательное JSON-экранирование. JSON остаётся компактным. Это настройка JSON-транспорта; сериализация OAuth-хранилища не менялась.
- Документ `contexts/codex_websocket_implementation.md` пользователь считает рекомендацией, а не обязательным ТЗ. Приоритет у текущих DTO и решений в диалоге. Не менять `SummaryTimestamp` на string; отдельный revision не нужен. Keychain не добавлять.
- Добавлены `IModelSelector`, `LLMModel` в core и `ConsoleModelSelector` в console, зарегистрированы в DI. Коннектор после OAuth получает аккаунтный `GET /v1/models`, отбирает `visibility=list`, показывает display_name, использует выбранный slug. Жёстко заданной модели нет.
- Выбор reasoning effort реализован после выбора модели. LLMModel содержит ReasoningLevels (effort/description) и DefaultReasoningEffort из supported_reasoning_levels/default_reasoning_level каталога аккаунта. ConsoleModelSelector показывает допустимые уровни; Enter выбирает объявленный default, 0 — server default без параметра reasoning. Если уровни не объявлены, используется server default. Уровни фильтруются по значениям Responses API (none/minimal/low/medium/high/xhigh/max); ultra с автоматическим делегированием не предлагается. ChatGPTConnector проверяет выбранный effort по исходной модели каталога; ResponsesConnection хранит его и передаёт reasoning.effort при warmup, Session, DialogRequest и восстановлении. Выбор фиксируется на запуск приложения; DTO сессии и диалога не менялись. CancelAsync добавлен в интерфейс коннектора; отдельный консольный хоткей экстренной отмены пока не назначен.
- `ILLMSessionLifecycle` удалён вместе с callbacks ConfigureSession/acceptResponse/acceptRecovery и ConfigureDialogRestoration. `ILLMConnector` имеет IsBusy, InitializeAsync, ReconnectAsync, CancelAsync, InitializeSession(instructions, Session), SendRequest(DialogRequest, continuation) и обычное событие ConnectionLost. Коннектор не вызывает модель и не принимает решений о подтверждении ответа.
- Ответ коннектора — LLMResponse(Payload: DialogResponse, Continuation: ILLMContinuation). Продолжение непрозрачно для core, содержит ConnectionId, IsValid, Retain/Dispose. В провайдере это независимые Retain/Dispose-указатели на серверный response.id и socket. Именованных потоков и закрепления серверного кеша больше нет; при previous_response_not_found выполняется восстановление. DTO Session/Request/Response не менялись.
- `SessionModel.SendRequestAsync` формирует снимок и сохраняет локальные параметры запроса в async-операции, удерживает копию continuation, ждёт сеть вне блокировки, сам проверяет request_id/error/summary/summary_ts. При успехе под Lock заменяет один immutable ConfirmedState (ID, summary, граница, continuation); ошибка оставляет прежнее состояние, устаревший ответ возвращает null. Отдельные публичные GetRequest/Reset/IsCurrentResponse/CompleteRequest удалены. GetSession оставлен для снимка полной Session.
- Контроллер вызывает только model.SendRequestAsync и выводит ненулевой ответ. `_lastPrintedAnswerId` — только защита порядка отображения уже принятых ответов при переупорядочении task continuations; бизнес-решение принимает только модель.
- `DialogCoordinator` — общий DI singleton для модели и контроллера, оборачивает ITextProcessor и синхронизирует ProcessAsync/ReloadAsync вместе с уведомлениями MessageCompleted/HistoryReplaced. Контроллер подписывается для одиночного вывода либо Clear + пакетного вывода; модель и процессор не обращаются к IOutput. Callback восстановления в контроллер удалён.
- `ResponsesSocket` — ClientWebSocket, Authorization Bearer, TLS, keepalive и сборка фрагментированных текстовых сообщений. По команде пользователя KeepAliveTimeout увеличен с 20 секунд до 1 минуты после разрыва при ожидании Pong во время первой инициализации Session; KeepAliveInterval остаётся 20 секунд. `ResponsesConnection` — один reader и последовательные операции; `ResponsesProtocol` — создание событий и проверка ответов.
- На новом соединении warmup (`developer`, `generate=false`), затем JSON Session (`user`), затем JSON DialogRequest. `store=false`, без stream_id, JSON Schema при генерации. Успех требует response.completed/status=completed; частичные deltas не применяются. Завершённые response.output_item.done клонируются в текущий Pending по output_index; при пустом терминальном output из них собирается ответ. Если терминальный output заполнен, используется он без дублирования текста. Ошибки и отмена отбрасывают накопленные элементы. Refusal, ошибки API, неверный JSON/структура/request_id/summary_ts не коммитят состояние.
- Серверный ID previous_response_id скрыт в continuation. Коннектор не хранит отдельный confirmedResponseId: подтверждённый указатель принадлежит SessionModel рядом с саммари. Транспорт проверяет структуру JSON, модель — смысл и актуальность ответа.
- По последнему решению пользователя параллелизм LLM удалён: один активный запрос, без очереди и без stream_id. Транспорт хранит один Pending и сопоставляет события по response.id; пулы потоков, слоты, fork и drain удалены. IsBusy выставляется атомарно до начала операции и сбрасывается в finally; попытка нового SendRequest/InitializeSession при занятости вызывает InvalidOperationException. SessionModel проверяет IsBusy и защищает всю операцию до применения ответа своим признаком занятости. Аудио и транскрибация продолжаются независимо.
- CancelAsync работает только при активной операции: отменяет её токен, физически закрывает WebSocket, ждёт завершения операции и reader; ConnectionLost запускает восстановление в SessionModel. Метод защищён SemaphoreSlim: повторные вызовы во время отмены пропускаются без очереди, дополнительно проверяется идентичность целевой операции. На время очистки IsBusy остаётся true. В простое CancelAsync ничего не делает. Прежний ResponseTimeout (2 минуты) сохранён; по его истечении или отмене вызывающим токеном незавершённая генерация также прерывается закрытием сокета, чтобы после снятия занятости не оставить скрытый параллельный запрос.
- Разрыв/таймаут/экстренная отмена/непригодная цепочка запускают реконнект с повторным warmup и свежей Session. Прерванный запрос НЕ повторяется; пользователь решает сам после сообщения о готовности. Подготовленные до восстановления запросы не посылаются в новую цепочку со старым саммари.
- Восстановленное саммари заменяет старое только в памяти; истории и саммари не сравниваются и не оптимизируются удалением ранних записей. Фрагменты, поступившие после отправленного снимка, остаются для следующих raw_records.
- Подключены сохранение и восстановление: TextProcessor реализует IReloadableTextProcessor. ProcessAsync добавляет фрагмент в память и буфер, затем пытается сохранить весь буфер через AddSessionMultipleDialogRecordsAsync. Метод IDatabase/SQLite атомарно добавляет весь пакет; AddSessionDialogRecordAsync сохранён в контракте, но рабочий процесс его не использует. ReloadAsync полностью заменяет _dialog объединением снимка GetSessionAsync и остатка буфера и сбрасывает _pendingMessage. Эти операции сериализованы общим SemaphoreSlim, поэтому записи во время перезагрузки ожидают её, а загрузка ожидает незавершённое сохранение. Ошибка чтения сохраняет прежнюю историю; ошибка записи логируется, а фрагменты остаются в памяти и буфере. При DisposeAsync выполняется последняя попытка сохранения.
- При ConnectionLost модель делает IsReady=false и запускает восстановление: connector.ReconnectAsync, DialogCoordinator.ReloadAsync, новая Session с инструкциями. Бывшие ответы отсекаются по ConnectionId и request_id. Новая Session и DialogRequest используют один сквозной счётчик request_id. Восстановление имеет максимум попыток и отменяется при Dispose; повторный разрыв во время завершающей стадии не оставляет ложное состояние Ready.
- Контроллер ожидает ProcessAsync, поэтому WaitForIdleAsync включает сохранение в БД. Время захвата теперь UTC; Local-время прямых вызовов процессора приводится к UTC согласно семантике SQLite. Синхронный Process оставлен для совместимости; в приложении используется асинхронный путь. Альтернативный SessionFileTextProcessor не менялся.
- Параметры: ChatGPTConnectorOptions — таймаут подключения 30 с и ответ 2 мин; SessionRecoveryOptions в core/DI — Delay 2 с и Attempts 3 (перенесены из настроек провайдера). Refresh OAuth сохраняет ротированные токены прежним способом; 401/403 останавливают восстановление без бесконечных повторов. После исчерпания попыток — ошибка в логах и рекомендация перезапуска.

По пункту 4 пользователь принял существующую временную границу без дополнительных изменений. Пункт 5 реализован очисткой и пакетным повторным выводом истории. ## Реализация SQLite

- Добавлен `aissyst.sqlite` в решение и ссылку тестового проекта. Зависит от core и `Microsoft.Data.Sqlite` 10.0.13. Core не зависит от SQLite.
- Публичный класс `aissyst.sqlite.SqliteDatabase(string databasePath)` реализует все методы `IDatabase`. Нужен путь к файлу; `:memory:` не поддерживается. Каталог и схема создаются лениво при первом обращении.
- Таблицы `contexts`, `context_blocks` (FK `context_id`), `sessions` (включая `name`, `creation_time`, инструкции, preview и `context` как JSON-массив), `dialog_records` (FK `session_id`, отдельный integer ID, `ts`, `role`, `message`). Сессия не связана FK с исходным контекстом.
- Foreign keys включены, WAL, индексы по `context_id` и `(session_id, ts)`, `PRAGMA user_version=1`. Неподдерживаемые версии отклоняются; миграций пока нет.
- Каждая операция открывает/закрывает соединение (pooling отключён). Операции одного экземпляра сериализуются `SemaphoreSlim`; SQL выполняется в `Task.Run`, поскольку провайдер синхронный. Все операции имеют транзакцию, чтение использует согласованный снимок.
- Даты хранятся как UTC ticks с точностью 100 нс. Local преобразуется в UTC, Unspecified трактуется как UTC. Возвращаемые даты имеют Kind=Utc. При одинаковых ts записи не теряются, внутренний ID разрешает равенство при чтении.
- ZIP разбирается целиком до вставки без распаковки на диск. Переносы в теле блока сохраняются, BOM поддерживается. Начальные инструкции/preview обязательны; прочие корневые файлы и вложенные блоки игнорируются.
- Сессия копирует контекст транзакционно. Исходные фрагменты добавляются отдельно или вся история заменяется атомарно. Источник Both для одной реплики отклоняется. Роли: Microphone→interviewee, Application→interviewer, None→unknown.
- Экспорт: GZip + UTF-8 JSON, `format_version`, `name`, `creation_time`, `instructions`, `preview`, `context` и `dialog`. ID не экспортируются. В целевой базе выдаётся новый локальный ID (численно может совпасть с ID в другой базе), время и имя сохраняются.
- Экспорт сначала пишет временный файл рядом с целевым, затем заменяет целевой файл. Импорт проверяет десериализацию, обязательные поля и версию до транзакции. Контекст в целевой базе не требуется.
- Отмена проверяется между этапами и записями, перед commit; уже выполняющийся SQL не прерывается. Ошибки не скрываются: отсутствие сущности — KeyNotFoundException, неверные архивы/JSON — InvalidDataException (некорректный UTF-8 — ошибка декодирования), ошибки SQLite передаются вызывающему коду.
- Добавлен английский `aissyst.sqlite/README.md`; обновлены корневой и Database README. `.gitignore` исключает SQLite-файлы/sidecar, но явно разрешает каталог проекта `aissyst.sqlite`.

### Консольная инициализация сессии

- Дополнение по команде пользователя: после выбора номера сессии доступны `(o)open`, `(n)return to list`, `(d)delete`; для контекста — `(c)create new session`, `(n)return to list`, `(d)delete`. Клонирование сессий не предусмотрено.

Удаление транзакционное; отсутствующий ID вызывает `KeyNotFoundException`. Каскад удаляет блоки контекста или диалог сессии. Удаление контекста не затрагивает сессии.

- Реализован `aissyst.console/ConsoleSessionSelector.cs`: нумерованный список сессий с именем и UTC-временем, `Create New`, затем список контекстов и `Create from Template`.

- Импорт шаблона сразу создаёт и выбирает сессию. Имя контекста берётся из имени архива. Пути с пробелами и обрамляющими одинарными/двойными кавычками поддерживаются.
